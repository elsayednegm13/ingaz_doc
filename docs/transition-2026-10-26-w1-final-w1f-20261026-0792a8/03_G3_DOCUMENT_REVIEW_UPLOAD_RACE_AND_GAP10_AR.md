# 03 — G3: سباق مراجعة المستند ورفع نسخة جديدة + تحليل GAP-10

- **البوابة:** `G3` — `DOCUMENT_APPROVAL_UPLOAD_RACE`
- **الحكم:** `PASS` بعد إصلاح المنتج، مع دليل قبل/بعد على مصدر غير معدّل ثم معدّل.
- **GAP-10:** `BLOCKED_CONTRACT` — تحليل فقط، بلا تعديل schema وبلا `0010`.

## 1. الخلل قبل الإصلاح

`reviewDocument` كان يقرأ حالة المتطلب وآخر نسخة، ثم يكتب:

1. تحديث حالة المتطلب.
2. إدراج صف مراجعة.
3. تحديث `document_versions.review_state`.

بين القراءة والكتابة يمكن لطلب رفع أن يُنشئ **نسخة أحدث** ويعيد حالة المتطلب إلى
`UPLOADED`. النتيجة: اعتماد يُسجَّل على نسخة قديمة بينما أحدث ملف لم يُراجَع، ويصبح
المتطلب `APPROVED` مع أن آخر نسخة `UPLOADED`. هذا ليس تعارضًا شكليًا؛ هو اعتماد مستند
لم يره المعتمد.

## 2. الدليل قبل الإصلاح (محفوظ)

| المحاولة | النتيجة | التفصيل |
|---|---|---|
| `attempt-14` | FAIL | شوهد الاعتماد القديم فعليًا، ثم توقف السيناريو على `409 DOCUMENT_ALREADY_EXISTS` لأن سيناريو الاختبار أضاف نوعي مستند متطابقين. خلل هارنس، لا خلل منتج إضافي. |
| `attempt-15` | FAIL | بعد إصلاح الهارنس (أنواع مستندات مختلفة): 24 فحصًا، فشل واحد فقط هو الخلل المقصود. |

تفصيل `attempt-15`:

```json
{"req_status":"APPROVED","versions":2,"max_version":2,"reviewed_version":1,"latest_state":"UPLOADED","reviews":1}
```

أي: المتطلب معتمد، وآخر نسخة (v2) ما زالت `UPLOADED`، والمراجعة الوحيدة على v1.
هذا دليل Runtime حقيقي على الاعتماد القديم.

`attempt-14` لم يُحذف رغم أنه لم يكمل؛ هو سجل لخلل اختبار وليس دليل نجاح.

## 3. الإصلاح

القراءة تبقى للتحقق السريع وإرجاع أخطاء واضحة، لكن **الحارس الحقيقي داخل جملة الكتابة**:

```sql
UPDATE operation_document_requirements
   SET status = ?, waived_reason = ?, updated_at = ?
 WHERE id = ?
   AND status = ?                      -- الحالة التي راجعها المستخدم
   AND NOT EXISTS (
         SELECT 1 FROM document_versions v2
          WHERE v2.requirement_id = ?
            AND v2.version > ?          -- لا نسخة أحدث من المراجَعة
       );
```

وكل كتابة تابعة تحمل نفس الشرط:

- `INSERT INTO document_reviews ... SELECT ... WHERE NOT EXISTS (نسخة أحدث)`.
- `UPDATE document_versions SET review_state = ? WHERE id = ? AND NOT EXISTS (نسخة أحدث)`.

ثم يُفحص `meta.changes`:

| الحالة | النتيجة |
|---|---|
| المتطلب تغيّر مرة واحدة والمراجعة أُدرجت | يُكمل: حدث الحالة، التدقيق، إعادة حساب التذكيرات |
| `changes = 0` | `409 DOCUMENT_CHANGED` **قبل** أي تدقيق أو تذكير أو حدث حالة |
| مراجعة مكررة لنفس القرار | `200` بلا صف مراجعة ثانٍ |

لا يوجد `DELETE` ولا كتابة تعويضية؛ الحارس يمنع الكتابة من الأصل.

## 4. الدليل بعد الإصلاح — `attempt-16` (PASS، 24 فحصًا)

### 4.1 سباق 1: موافقة أثناء رفع نسخة ثانية

| القياس | النتيجة |
|---|---|
| رفع v2 | `201` |
| المراجعة المتزامنة | `409 DOCUMENT_CHANGED` |
| حالة المتطلب بعد | `UPLOADED` |
| عدد النسخ | `2` |
| آخر نسخة | `v2` |
| النسخة التي راجعها الطلب | `null` — لم تُسجَّل مراجعة |
| حالة آخر نسخة | `UPLOADED` |
| صفوف المراجعة | `0` |
| اعتماد قديم؟ | `false` |

الأهم: **صفر آثار جانبية**. لم يُكتب صف مراجعة، ولم يُكتب حدث حالة، ولم يُحدَّث
`review_state`، ولم تُعدَّل التذكيرات. الطلب فشل نظيفًا وأعاد 409 مفهومًا.

### 4.2 سباق 2: الرفع أولًا ثم المراجعة

| القياس | النتيجة |
|---|---|
| رفع v2 | `201` |
| وضع `UNDER_REVIEW` | `200` |
| اعتماد | `200` |

| النسخة المراجَعة | `v2` — الأحدث |

هذا يثبت أن الإصلاح لا يمنع المراجعة المشروعة بعد الرفع؛ إنما يمنع المراجعة على نسخة قديمة.

## 5. GAP-10 — احتفاظ idempotency وحذف المستخدم

### 5.1 الوصف الدقيق

من `0005_idempotency.sql`:

```sql
actor_id TEXT NOT NULL REFERENCES user(id) ON DELETE CASCADE
```

سجل `idempotency_keys` هو **الشاهد الدائم** على أن طلبًا معيّنًا نُفّذ وماذا أعاد. ربطه
بـ`ON DELETE CASCADE` يعني أن حذف المستخدم — لأي سبب مستقبلي — يمحو شواهد كل عملياته.

### 5.2 ما أُثبت فعليًا

| الفحص | النتيجة |
|---|---|
| إنشاء طلب بمفتاح idempotency | `201` |
| عدد الشواهد قبل | `1` |
| حذف المستخدم خارج مسار المنتج (SQL مباشر) | `exit=0` |
| عدد الشواهد بعد | `0` |
| صف المستخدم بعد | `0` |
| مسارات `DELETE /users` المدعومة في المنتج | **`0`** |

الخلاصة الدقيقة:

- **لا يوجد اليوم مسار منتج يمحو الشاهد**، لأن المنتج لا يوفّر حذف مستخدم.
- لكن **السياسة غير محسومة**: أي أداة إدارية أو مسار مستقبلي للحذف/الاحتفاظ سيمحو الشاهد
  تلقائيًا بفعل الـFK.
- السؤال قرار مالك/عقد: هل الشاهد يُحفظ بعد حذف المستخدم (RESTRICT / SET NULL / أرشفة)
  أم يُمحى (CASCADE)؟ وما مدة الاحتفاظ؟ وكيف يتوافق ذلك مع حق المحو؟

### 5.3 لماذا `BLOCKED_CONTRACT`

1. تغيير سلوك الـFK يحتاج migration جديدة (`0010`)، وهي **غير مصرّح بها** في هذا الأمر.
2. لا يمكن اختيار `RESTRICT` أو `SET NULL` بلا قرار احتفاظ صريح من المالك.
3. لا يجوز «إصلاح» ذلك بتعديل `0005` بأثر رجعي؛ الترحيلات forward-only.
4. لا يوجد مسار منتج حالي يستدعي الحذف، فالتأثير Theoretical اليوم، لكنه Contract gap
   يجب حسمه قبل أي ميزة إدارة مستخدمين/احتفاظ.

### 5.4 حالة `0010`

| العنصر | الحالة |
|---|---|
| ملف `0010` | **غير موجود** |
| تطبيق `0010` | **لم يُطبَّق** |
| تعديل `0001..0008` | **لم يحدث** (drift = 0) |
| التحليل | موثّق هنا وفي `07` |

## 6. ما لا يثبته هذا الدليل

1. لا يثبت سباقًا على D1 البعيدة؛ كل شيء محلي.
2. لا يثبت أن كل مسارات كتابة المستندات محمية؛ يثبت مسار المراجعة تحديدًا.
3. لا يثبت أن `WAIVED` ثم رفع نسخة جديدة يعمل بكل توليفاته؛ الحالة مغطاة في E2E لكن ليس هنا.
4. GAP-10 لا يثبت خطرًا حاليًا في المنتج؛ يثبت **فجوة عقد** في سياسة الاحتفاظ.
