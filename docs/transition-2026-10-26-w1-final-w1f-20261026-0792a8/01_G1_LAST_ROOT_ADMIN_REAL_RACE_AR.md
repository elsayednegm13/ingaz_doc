# 01 — G1: آخر مدير جذر فعلي تحت تزامن حقيقي

- **البوابة:** `G1` — `LAST_ROOT_ADMIN_REAL_CONCURRENCY`
- **الحكم:** `PASS` بدليل Runtime حقيقي بعد إصلاح المنتج.
- **الأساس:** Worker حقيقي + Better Auth حقيقي + D1 محلية داخل جذر ملك الجولة، وطلبات HTTP متزامنة فعلية.
- **الجذر:** `.wrangler-safety-20261021-w1f-g1-post-0792a8` و`.wrangler-safety-20261021-w1f-g1-post2-0792a8`.

## 1. الخلاصة

الخلل قبل الإصلاح لم يكن في «قفل» بل في **تعريف من هو المدير الجذري**. كان العدّ يعتمد على
وجود دور `administrator` فقط، بينما التفويض الفعلي في المنتج يُحسب من:

```
(منح الدور) ∪ (تجاوزات GRANT المباشرة) − (تجاوزات DENY المباشرة)
```

مع شرط `user.is_active = 1`. لذلك كان بإمكان المسار القديم:

1. اعتبار مستخدم **غير فعّال** أو **محجوب بـDENY** «جذرًا» وهو ليس كذلك، فيسمح بتعطيل آخر جذر حقيقي.
2. اعتبار مستخدم يملك **GRANT مباشرًا** (بلا دور administrator) غير جذري، فيمنع تعطيله ويحصي أصفارًا.
3. السماح بترك النظام بلا أي جذر فعّال، أي `roots = 0`.

بعد الإصلاح، الطلبات المتزامنة الحقيقية أنتجت في كل محاولة **نجاحًا واحدًا فقط**، وبقي
`effectiveRootCount = 1`، ولم يظهر أي `5xx`.

## 2. تعريف الجذر الفعلي بعد الإصلاح

أُضيف تعبير SQL واحد مشترك في `server/services/users.ts`:

```sql
effectiveRootCondition(alias) =
  EXISTS (
    SELECT 1
      FROM user_roles ur
      JOIN roles r ON r.id = ur.role_id
     WHERE ur.user_id = <alias>.id
       AND r.key = 'administrator'
  )
  OR EXISTS (
    SELECT 1 FROM user_permission_overrides o
     WHERE o.user_id = <alias>.id
       AND o.permission_key = 'users.manage'
       AND o.effect = 'GRANT'
  )
  AND NOT EXISTS (
    SELECT 1 FROM user_permission_overrides o
     WHERE o.user_id = <alias>.id
       AND o.permission_key = 'users.manage'
       AND o.effect = 'DENY'
  )
  AND <alias>.is_active = 1
```

التعبير نفسه يُستخدم في:

- `countRootAdmins(db)` — لحساب الجذور الفعّالة.
- `setUserActive(...)` — داخل `UPDATE` ذرّي **يعيد فحص جذرية الفاعل نفسه** في SQL، لا في
  JavaScript قبل الكتابة.

بهذا لا توجد نافذة بين «قرأت أنني جذر» و«كتبت التعطيل»: الشرط جزء من جملة الكتابة.

## 3. الإعداد التجريبي

| العنصر | القيمة |
|---|---|
| المسار | `POST /api/v1/users/:id` عبر الـWorker الحقيقي |
| المصادقة | Better Auth حقيقي، جلسات حقيقية، كلمات مرور مولّدة لكل مستخدم |
| قاعدة البيانات | D1 محلية تحت `<runRoot>/state` بعد تطبيق `0001..0008` فقط |
| التزامن | طلبان يُطلقان معًا عبر `Promise.all` مع تأخير محقون `W1_ACTIVE_DELAY_MS=250` |
| عنوان الجلسة | IP اصطناعي مستقل لكل جلسة (`10.20.x.y`) مع `TRUST_CF_CONNECTING_IP=1` لتفادي rate limit |
| ملكية البيانات | كل مستخدم/دور/حالة أُنشئت داخل الجولة، ونُظّفت في نهايتها |
| البورتات | 44017–44024 (كلها مغلقة بعد التشغيل) |

**حدود حقن الخطأ:** التأخير فقط، ويُقرأ من متغيّرات Worker في config مولّد داخل جذر الجولة.
لا Header ولا Cookie ولا Query ولا Body يستطيع تفعيله. كل طلب يمرّ عبر التطبيق الحقيقي،
والصلاحيات الحقيقية، وD1 الحقيقية.

### 5.1 سباق التعطيل المتماثل (12/12)

| القياس | النتيجة |
|---|---|
| محاولات متزامنة | 12 |
| تداخل زمني فعلي | 12/12 (`overlap=true`) |
| نجاح واحد لكل محاولة | 12/12 (`successCount=1`, `rejectedCount=1`) |
| حالات النجاح/الرفض | `[200,403]` أو `[403,200]`، وحالة واحدة `[200,401]` |
| رموز الرفض | `USER_NOT_AUTHORIZED` أو `SESSION_EXPIRED` عند تعطيل جلسة الخصم |
| `effectiveRootsAfterRace` | `1` في كل المحاولات |
| أخطاء `5xx` | `0` |

مثال على تداخل حقيقي (المحاولة الأولى):

```text
request A: sent 1793048941454 → ended 1793048942732 (1278ms)
request B: sent 1793048941457 → ended 1793048942700 (1243ms)
overlap=true
```

الطلب `401` ليس استثناءً: عندما ينجح أحد الطرفين في تعطيل الآخر، تُبطَل جلسة الخصم قبل أن
تصل كتابته، فيُرفض بـ`401`. الثابت المطلوب هو **نجاح واحد فقط ولا صفر جذور**، وقد تحقق.

### 5.2 السباق المتقاطع (8/8)

| القياس | النتيجة |
|---|---|
| محاولات | 8 |
| الحالات | `[403,200]` في 8/8 |
| الرمز | `USER_NOT_AUTHORIZED` للطرف المرفوض |
| `effectiveRootsAfterRace` | `1` في 8/8 |
| `5xx` | 0 |

الترتيب هنا `DENY-first` لأن التأخير يُطبَّق على المسار النشط فقط؛ الطرف الذي يقرأ أولًا يرى
أنه لم يعد جذرًا فيُرفض. الترتيب المعاكس (تعطيل أولًا ثم محاولة الفاعل المعطَّل) مغطى
بفحوص حتمية منفصلة: إزالة الدور الذاتي وDENY الذاتي.

### 5.3 الفحوص السلبية والحتمية

| الفحص | النتيجة |
|---|---|
| تعطيل جذر بواسطة مستخدم غير مخوّل | `403` |
| إزالة الدور الذاتي لآخر جذر | `409 LAST_ADMIN`، الدور قبل/بعد = `1/1` |
| DENY ذاتي على `users.manage` لآخر جذر | `409 LAST_ADMIN`، التجاوزات قبل/بعد = `0/0` |
| جذر وهمي (دور بلا فعالية) | `409 LAST_ADMIN`، الجذور الفعّالة تبقى `1` |
| جذر «منح فقط» | `409 LAST_ADMIN`، الجذور الفعّالة تبقى `1` |
| تعطيل ثم إعادة تفعيل | `200/200` مع بقاء جذر فعّال واحد على الأقل |
| تعطيل مستخدم عادي بواسطة جذر | `200` |

### 5.4 حالة قاعدة البيانات بعد التهيئة النهائية

من `result.json` للمحاولة `attempt-07`:

```json
{"effectiveRootCount":1,"roleRootCount":9,"sessionCount":22,"auditCount":89}
```

هذا هو جوهر الإصلاح: **9 مستخدمين ما زالوا يحملون دور administrator، لكن واحدًا فقط جذر
فعّال** بعد تعطيل الباقي. لو كان العدّ يعتمد على الدور وحده لظهر `9`، ولَسُمح بتعطيل الجميع.

## 7. ما لا يثبته هذا الدليل

1. لا يثبت سلوك D1 البعيدة؛ كل شيء محلي.
2. لا يثبت تزامنًا على أكثر من نسخة Worker واحدة؛ بيئة workerd محلية واحدة.
3. التأخير محقون في مسار نشط واحد؛ لذلك ترتيب `cross` ثابت. الترتيب المعاكس مغطى حتميًا لا تزامنيًا.
4. لا يثبت أن كل مسارات إدارة المستخدمين محمية؛ يثبت مسار التعطيل/التفعيل ومسار الأدوار
   والتجاوزات كما تمرّ عبر الواجهة البرمجية الحقيقية.
