**المدخلات:** قرارات المالك الـ45، إجابات OD-01..OD-08 الإضافية، `BR v0.3`، والتقرير الأخير المرسَل عن `ET-2026-10-23-B`.

## 0) ماذا تعني «100% جاهز للاستخدام»؟

لا توجد طريقة هندسية موثوقة تضمن «خلو البرنامج من كل خطأ 100%». في هذا المشروع تعني العبارة **100% من نطاق العمل الذي يعتمد المالك تسليمه، مقبولًا ومُثبتًا بالتجارب والاختبارات، مع عدم وجود مخاطر حرجة معروفة تمنع التشغيل**. ليست مساويةً لـ100% تغطية كل سطر كود، ولا مجرد وصول الاختبارات إلى 53/53، ولا إلى مجرد نشر رابط.

**تعريف النجاح النهائي (جميع الشروط إلزامية):**

1. كل وظيفة إلزامية في **Business Requirements v1.0 الموقّعة** لها شاشة/API وصلاحيات وتعامل مع الأخطاء وإجراء قبول مثبت؛ لا ميزة إلزامية بحالة NOT_IMPLEMENTED أو PARTIAL.
2. **100% من سيناريوهات التشغيل الحرجة** في مصفوفة قبول واقعية يمر أمام مستخدمين فعليين؛ يوافق مالك المشروع وممثل قسم التصدير على نتيجة UAT مكتوبة. كل سيناريو تتبع له evidence ومخرجات متوقعة.
3. **صفر عيوب P0/P1 أو مخالفات أمن/سلامة بيانات مفتوحة** عند Go-Live؛ أي خطر متبقٍ من تصنيف أقل يوثق ويقبله المالك صراحةً، ولا يؤثر على عمل أساسي.
4. عزل بيئات الاختبار مثبت في **البداية وأثناء التشغيل وعند الإغلاق والفشل**؛ جميع الجذور التاريخية والمطور والملفات السرية محمية.
5. ترحيلات D1 الرسمية القديمة والجديدة نجحت على بيانات اصطناعية مأهولة مع إثبات حفظ السجلات والقيود والعلاقات، ثم نُفذت **مناورة نشر Staging وخطة نسخة احتياطية/استرجاع** بعد تفويض بيئي محدد؛ لا ترحيل مباشر لقاعدة المطور.
6. اختبارات Worker/Hono/Better Auth/D1/R2 والتكامل الحقيقي وE2E على المصدر النهائي **ناجحة مرتين متتاليتين على بيئتين معزولتين جديدتين**، مع تحقق من الصلاحيات والتزامن والتنبيهات.
7. توافق كامل مع الهوية البصرية المعتمدة عبر العربي RTL والإنجليزي LTR والأجهزة المستهدفة، واختبار الوصولية والأخطاء والـPDF/الطباعة؛ ليس مجرد غياب horizontal overflow.
8. تحقق الأداء تحت حجم عمل **يُتفق عليه مسبقًا** بناءً على واقع الشركة (مستخدمون متزامنون، عمليات/يوم، ملفات وحاويات، أحجام CSV وPDF، حدود D1/R2) مع عتبات `p95` و`p99` وخط أساس وتقارير؛ لا نحول أرقام اختبارات محلية إلى وعود إنتاج.
9. تجربة Staging/UAT كاملة ببيانات تدريبية أو بيانات مصرح بها، مع اختبار النسخ الاحتياطي، الاسترجاع، الصلاحيات، سجلات التدقيق، مراقبة الأعطال، ودليل تشغيل وتدريب الموظفين.
10. موافقات منفصلة على **نشر Staging** ثم **Production**، ونجاح فحص الصحة ومراقبة ما بعد الإطلاق وفق فترة تقييم يحددها المالك وخطة تراجع قابلة للتنفيذ. لا إصدار دون قرار GO موثق.

**المخرج النهائي:** `RELEASE_ACCEPTANCE=GO` و`OWNER_UAT=APPROVED` و`PRODUCTION_ACCEPTANCE=APPROVED`، مع دفتر أدلة قابل للتدقيق. قبل ذلك يبقى `NO_GO` مهما كانت نسبة الاختبارات.

## 2) القاعدة الذهبية لكل مرحلة

**لا يكفي برومت واحد يطلب تنفيذ المشروع حتى النهاية دون بوابات.** العمل يتحرك بقرار مالك محدد النطاق لكل مرحلة:

`READ-ONLY BASELINE → OWNER SCOPE GO → IMPLEMENT IN ISOLATION → UNIT/CONTRACT/INTEGRATION/E2E PROOF → DELTA / DATA / ACL / GIT IMPACT REVIEW → OWNER GO/NO-GO → NEXT STAGE`.

كل مرحلة: (أ) ترجع لبصمات المصدر الحالي، (ب) لا تزيل أدلة تاريخية، (ج) تنشر جدول تغييرات حقيقي، (د) تحقق مسارات الفشل والارتداد والتزامن، (هـ) لا تنتقل تلقائيًا إلى التالية، (و) تخرج بتقرير عربي وملفات أدلة. عند P0/P1 أو خرق عزل أو فقدان تاريخ/صلاحيات، `STOP` فورًا وتقرير `NO_GO`.

**الهدف:** جمع المهام في شاشة تشغيل واحدة تقلل النسيان.  
**العمل:** واجهة Premium Operations Workspace المعتمدة كاتجاه، مركز عمليات يبرز UCR المعلّق والتحميل وCut-off ونواقص المستندات والفواتير والتسليم؛ تذكير لكل موعد مع قراءة/تجاهل/إيقاف مستقل، browser notifications بعد إذن المتصفح، لا بريد إلكتروني إلا ضمن نطاق منفصل؛ ضبط IANA TZ/DST وفق BR، Cron idempotency/concurrency ومنع تضخيم D1؛ صلاحية all-cases reports منفصلة عن case-scoped; Public Tracking links محدودة بلا بيانات مالية أو مستندات.  
**معيار القبول:** UI AR/EN متكافئة، لا بيانات KPI وهمية، التذكيرات القديمة لا تعود بعد تغيير الموعد، لا تضخم jobs؛ تقارير CSV لا تسرّب؛ روابط التتبع تنتهي وتُلغى.  
**الحالة الآن:** `EXISTING FUNCTIONALITY / TARGET ACCEPTANCE NOT COMPLETE`.

### M10 — تدقيق متكامل، أمن، أداء، استرداد، QA/UAT
**الهدف:** إثبات النظام كمنتج، لا كملفات كود منفصلة.  
**العمل:** اختبارات happy path + negative + ACL/BOLA + race + idempotency + legacy data + R2 security + audit + calendar DST + offline/retry + browser + API contracts + accessibility + PDFs. تنفيذ E2E على بيئتين/مرتين معزولتين بالمصدر النهائي، ثم اختبارات حمل ممثلة وحدود D1، سيناريوهات WIP/reminders الكبير. تجهيز قائمة UAT يوقعها موظفو قسم التصدير.  
**معيار القبول:** جميع السيناريوهات الحرجة PASS؛ 0 عيوب P0/P1؛ أي P2 متبقٍ له قبول صريح، لا سيناريو حرِج NOT_RUN/BLOCKED؛ المستندات والإذن/التدقيق قابلة للمراجعة.  
**الحالة الآن:** `NOT ACHIEVED`.

### M11 — Staging مستقلة ومناورة الإطلاق (تفويض منفصل)
**الهدف:** إثبات صلاحية Cloudflare D1/R2/Worker الحقيقية قبل التأثير على الإنتاج.  
**العمل:** بعد تفويض صريح، إنشاء Staging بمعرفات D1/R2/secrets معزولة لا تشارك إنتاجًا/مطورًا؛ تطبيق نسخ ترحيل مُختبرة، اختبار Auth وupload/download وCron وR2 private وRBAC والـPDF والتنبيهات؛ إجراء تدريب وUAT حقيقي ومراقبة وتقرير سحابي. إعداد Runbook backup/restore، versioned deployment، rollback وسجلات تدقيق.  
**معيار القبول:** Staging-UAT موافق عليه، اختبارات الترحيل والاسترجاع والمراقبة والأداء والأسرار والحدود ناجحة، قرار مستقل GO للإنتاج.  
**الحالة الآن:** `NOT AUTHORIZED / NO_GO`.

### M12 — Production Go-Live واعتماد التشغيل (تفويض مستقل)
**الهدف:** بدأ العمل الحقيقي لقسم التصدير مع قدرة استرجاع وتشغيل آمن.  
**العمل:** اعتماد مالك رسمي؛ خطة cutover للحالات التاريخية دون فقد، أدوار مستخدمين وصلاحيات، نسخة احتياطية قابلة للتحقق، نشر بإجراءات مراجعة change management، health checks، مستخدمون تجريبيون، تسجيل أول عملية حقيقية حتى الإغلاق، مراقبة تشغيل وتمارين استجابة للحوادث، دليل تدريب وإدارة، قبول بعد فترة الاستقرار المتفق عليها.  
**معيار القبول:** owner acceptance على الحالات الأساسية، لا حوادث P0/P1 غير معالجة، إمكانية تراجع مثبتة، فريق قادر على التشغيل اليومي، قبول حقيقي لشاشة الفاتورة والمستندات والحجز والتذكيرات والتقارير والأمان.  
**الحالة الآن:** `NO_GO`.

## 6) سجل التفويض وحدود الموارد

- كل مرحلة تتطلب **تكليفًا تنفيذيًا مستقلًا محددًا**؛ هذه الوثيقة خطة لا إذن. يمكن التخطيط لمراحل لاحقة خلال انتظار قبول الحالية، لكن لا تبدأ عملياتها تلقائيًا.
- **ممنوع مسّ `.wrangler/state`** فتحًا/قراءة/نسخًا/تعديلًا/ترحيلًا، وممنوع لمس `.dev.vars*` أو الأسرار، أو تغيير الجذور التاريخية `.wrangler-e2e`, `.wrangler-perf`, `.wrangler-reliability-*`, `.wrangler-transition-audit-*` إلا بإذن خاص وتقييم مسبق، وأصلًا لا حاجة لفتحها.
- تجارب الاختبار على بيانات اصطناعية وجذور جديدة، لا إعادة استخدام قواعد قديمة. لا قتل عمليات أجنبية.
- لا تعديل ترحيلات `0001..0008` التاريخية؛ أي تطوير جديد يراجع schema المصدر الفعلي ويستعمل ترحيلًا **إضافيًا** بعد رقم آخر migration مع ضمان توافق التاريخ.
- لا Git `commit/push/clean/reset/checkout/stash` ولا Cloudflare أو بيانات إنتاجية بدون تفويض صريح.
- لا إقرار جاهزية R2 عن طريق اختبار fake filesystem أو Playwright على SQLite مصطنعة فقط؛ لابد من Staging حقيقي مفوض.
- بعد كل مرحلة: مراجعة انتقال delta/impact بالأدلة، مقارنة قبل/بعد، اختبار الوحدات والتكامل المقصود، سجل ديون ومخاطر GO/NO-GO وقرار نطاق التالي.
