# 13 — مقترح إصلاح التعويض في المصادقة (Auth Compensation Remediation Proposal)

**التدقيق:** ET-2026-10-20 · **الحالة: `PROPOSED_NOT_APPLIED`** — لا كود ولا ترحيل ولا نشر سحابي.
**الهدف:** إغلاق AUTH-03/AUTH-06 (فشل التعويض نفسه) بطريقة **ضيّقة** لا تحتاج بنية سحابية جديدة.

## 13.1 المعيار: ما الذي يجب أن يتحقق بعد أي فشل؟

| # | المعيار | الحالة الحالية |
|---|---|---|
| C-1 | لا حساب **مفعّل** بلا دور ولا صلاحية | جزئي: التعويض يغطّي ذلك إذا نجح |
| C-2 | لا **مدير** جزئي فعّال | جزئي: نفس القيد |
| C-3 | الـBootstrap **لا يُbricked** | غير مضمون (فشل الـbatch ⇒ `bootstrap_consumed=1` باقٍ) |
| C-4 | الفشل **قابل للكشف** (لا صامت) | غير مضمون |
| C-5 | **مسار استرجاع** محدد (إعادة المحاولة أو تدخّل إداري) | غير موجود |
| C-6 | سجل التدقيق يبقى محفوظًا | نعم (19 صفًا في المقيس) |

## 13.2 الخيار (أ): «معالجة فاشلة» داخل نفس الـbatch (الأضيق — موصى به)

**الفكرة:** بدل الاعتماد على batch واحد يفشل كليًا، تنفيذ التعويض على **دفعات صغيرة** مع تسجيل كل خطوة.

| العنصر | التفصيل | الأثر |
|---|---|---|
| التنفيذ | استبدال `db.batch([...])` بـ **3 دفعات صغيرة**: (1) تحرير `bootstrap_consumed`، (2) حذف `account`+`session`، (3) حذف `user_roles`+`overrides`+`preferences`+`user` | فشل أي دفعة لا يمنع بقية الدفعات |
| الأولوية | **تحرير السرّ أولًا** ⇒ حتى لو فشل الباقي، الـBootstrap يبقى متاحًا (يُنشئ مديرًا ثانيًا فقط) | C-3 يتحقق |
| الترتيب | حذف `user` آخرًا ⇒ الـFK ON DELETE CASCADE ينظّف `user_roles` تلقائيًا | C-1/C-2 يتحققان |
| كشف الفشل | التقاط خطأ كل دفعة وكتابة `audit_log` صف بحالة `action='auth.compensation.failed'` و`after_json` بما لم يُحذف | C-4 يتحقق |
| الاسترجاع |Because the secret is released first، يكفي إعادة تشغيل الـBootstrap (عملية يدوية موثّقة) | C-5 يتحقق |
| مخطط | **بلا ترحيل** | لا تكلفة مخطط |
| esfuerzo | صغير (تعديل ~20 سطرًا في `app.ts` + `users.ts`) | |
| المخاطر | إظهار السرّ مُتاحًا مرة أخرى بعد فشل ⇒ إ.windowsisement: ي**نشّط** vectorOrchestrator (Bootstrap متاح بعد فشل) — لكن هذا هو المقصود (قابلية الاسترجاع)، والمفتاح يبقى في `BOOTSTRAP_SECRET` | |

**ملاحظة أمنية مهمة:** تحرير السرّ بعد الفشل يعني أن أي شخص يعرف `BOOTSTRAP_SECRET` يستطيع إنشاء مدير — **وهو أيضًا حال اليوم** (السريّة في متغيّرات البيئة). الخيار (أ) لا يزيد الخطر القائم، بل يجعله قابلًا للاستخدام.

## 13.3 الخيار (ب): «حالة تخصيص دائمة» (provisioning state)

**الفكرة:** جدول `user_provisioning` يتتبع كل محاولة إنشاء حساب حتى النجاح/الفشل.

| العنصر | التفصيل |
|---|---|
| المخطط | `user_provisioning (id, email, actor_id, state, created_user_id, failure_code, created_at, updated_at)` |
| التدفق | إنشاء سجل `PENDING` قبل `createUser`؛ تحديثه إلى `COMMITTED` بعد النجاح، أو `COMPENSATED`/`COMPENSATION_FAILED` عند الفشل |
| الفايدة | (1) **كشف** أي فشل تعويض (استعلام `state='COMPENSATION_FAILED'`)، (2) مسار استرجاع موثّق، (3) تتبّع تاريخي |
| التكلفة | ترحيل إضافي (إضافة فقط) + writes إضافية في مسار إنشاء المستخدم |
| أثر الخصوصية | يخزّن البريد — يجب أن يتبع نفس سياسة `audit_log` |

## 13.4 الخيار (ج): مهمة دورية + «حارس» (بدون بنية سحابية)

**الفكرة:** استغلال `handleScheduled` القائم (يُنفَّذ كل دقيقة عبر Cron في `wrangler.jsonc`).

| العنصر | التفصيل |
|---|---|
| الفحص | عدّ المستخدمين `is_active=1`who `must_change_password=1` وبلا `user_roles` |
| الإجراء | تعطيلهم (`is_active=0`) + `audit_log` + **لا** حذف (للحفظ الجنائي) |
| التردد |Cron موجود أصلًا ⇒ **لا بنية سحابية جديدة** (S07 يمنع) |
| الفايدة | يحوّل «حساب يتيم غير مكتشَف» إلى «حساب معطّل ومُسجَّل» |
| الحدود | Cron لا يصلح bootstrapped ⇒ لا يغطي AUTH-03/06 (يُغطّي غيرهما) |

## 13.5 المقارنة

| المعيار | (أ) دفعات + تحرير مبكر | (ب) حالة تخصيص | (ج) حارس دوري |
|---|---|---|---|
| C-1/C-2 (لا حساب بلا دور) | ✔ | ✔ | ✔ (تعطيل) |
| C-3 (لا brick) | ✔ | جزئي (يحتاج استرجاعًا يدويًا) | لا |
| C-4 (كشف) | ✔ (سجل) | ✔ (استعلام) | ✔ (استعلام) |
| C-5 (استرجاع) | ✔ (إعادة Bootstrap) | ✔ (إعادة المحاولة) | ✔ (تعطيل + تدخّل) |
| C-6 (تدقيق محفوظ) | ✔ | ✔ | ✔ |
| ترحيل جديد | **لا** | نعم | لا |
| بنية سحابية جديدة | **لا** | لا | لا |
| الجهد | صغير | متوسط | صغير |

## 13.6 التوصية

| الأولوية | الإجراء | السبب |
|---|---|---|
| **1** | الخيار (أ): تحرير السرّ **أولًا** + دفعات تعويض صغيرة + صف تدقيق عند الفشل | يغلق AUTH-03/06 بأقل تكلفة، بلا مخطط ولا بنية |
| **2** | الخيار (ج): حارس دوري لتعطيل الحسابات المعزولة | يضيف شبكة أمان-detect |
| **3** | الخيار (ب): جدول حالة التخصيص | للمتابعة على المدى الطويل والتدقيق الجنائي |

**لم يُطبَّق أيٌّ منها** — بانتظار قرار المالك (20-3).

## 13.7 خطّاف حقن الأخطاء المقترح (غير مطبَّق)

لإغلاق الفجوة **«لا يمكن قياس فشل التعويض»**، يلزم خطّاف حقن. **النموذج المقترح (بلا تطبيق):**

```ts
// server/http/app.ts — داخل catch الخاص بـ bootstrap
if (c.env.EXPORTFLOW_TEST_FAULTS === "1" && c.req.header("x-test-fail-compensation") === "1") {
  throw new Error("Induced compensation failure");
}
```

| analys| السمة | القيمة |
|---|---|---|
| التفعيل | `EXPORTFLOW_TEST_FAULTS=1` (غير مفعّل في الإنتاج) | نفس نمط `x-test-fail-before-handler` القائم في `app.ts:407-416` |
| الأثر في الإنتاج | **صفر** (المتغيّر غير مضبوط) | — |
| العيب الحالي | الخطّاف موجود **داخل شيفرة الإنتاج** ⇒ يُقترح نقله إلى وحدة اختبار/إعداد مخصّص | راجع 15.4 |

> هذا المقترح **نمط فقط** (S00.3: لا تعديل على `server/**`).
